# sanguo-battle-sim-gate · 战斗仿真门禁方法论

> 一套「改动必须过机器门禁」的战斗数值回归做法：批量自对弈仿真跑量，聚合分析器统一判红，异常分级处置，种子驱动配牌与洗牌，以聚合统计为验收口径。来自一个已上线的 3v3 回合制卡牌微信小游戏的服务端开发过程。本仓只公开口径、结构与脚本行为约定，不含引擎源码（见文末说明）。

## 解决什么问题

个人项目没有 QA，引擎和数值的每一次改动如果靠手感回归，必然漏。这个项目的做法是把「改坏了」变成机器可判定的问题：任何引擎或配置改动，必须先跑批量仿真自对弈、过聚合分析器判红，才允许合并；需要回答数值问题时（谁强谁弱），用同一套基础设施做全量评估。异常必须可复现、修复必须可证明——这两点决定了整套设计。

## 门禁口径（两个数字，是两件事）

- **回归门禁（每轮改动都跑）**：5 个代表阵容全矩阵 × 20 局 = **500 局**（默认种子 420000、八路并行，一杯咖啡的时间）。跑完不靠人眼看日志：聚合分析器统一判红，规则五级、优先级 5＞2＞3＞4＞0——
  - **5 环境失败**：连一个对局 JSON 都没有，或进度文件损坏——「跑没跑成」都无法判定；
  - **2 硬异常**：局崩溃 + hard 级异常行（对账/审计/生命周期），**零容忍**；异常分两级（hard / quality），quality 只记录不判红（如归因缺口），旧格式/坏行按 hard 计（fail-closed）；
  - **3 平衡体检**：baseline 阵容的胜率/回合数越出体检带（胜率 45–55%、回合中位 5–10、平局 ≤10%）且置信区间压线才判红——当前全部阵容为实验档，重锚轮后启用；
  - **4 覆盖不达标**：strict 档下覆盖账本未建立即判红（当前默认 warn 档，只高亮不判红；CI nightly 接入为阶段 3.5 预留）；
  - **0 绿**：以上全过。
  判定权在聚合分析器，跑量进程的退出码只作日志参考——「程序跑完」和「批次合格」是两件事。
- **强度评估（一次性专项）**：全英雄阵容组合 C(15,3)=455 套 × 每套 228 局 = **103,740 场**，全量跑完异常 0，产出强度榜、15×15 搭档矩阵与阵容梯度报表。
- 两者不可互相替代：门禁回答「这次改动有没有改坏」，评估回答「当前数值谁强谁弱」。混用口径是常见的表述事故——宣传「每轮 10 万场」或「500 局够平衡吗」，都问错了问题。

## 关键设计四则

**1. 种子驱动的随机与聚合口径**
随机源可注入：自动配牌与牌堆洗牌由种子驱动，同一 seed 得到同一副牌堆、同一套配牌——这是断点续跑以「阵容 × seed」为完成键的前提。工程实录：全量跑完后做跨进程对拍，发现逐行结果仍不可复现（骰子与战斗结算的几处随机源未接种子）；据此把验收口径修正为「聚合统计为有效口径」（同批次均值抖动 ≤0.04，十万场聚合足以抹平随机噪声），逐行复算列入已知改进项。如实记录这次修正：**断言要接受对拍检验。**

**2. 每场对局归约成一行数据**
仿真不落整局回放：每场的对局事件流在进程内归约成一行结构化 JSON——胜负、回合数、双方每个技能各档兑现了几次、伤害由哪些来源构成、每张牌出了几次。十万场跑完，磁盘只占 247 兆。报表与判红都只面对行级数据。

**3. 批次哈希隔离**
输出目录带阵容内容的哈希指纹（sha256 前 8 位）：阵容任何改动 = 新目录、新批次，断点续跑与聚合分析**永不混批**；跨批次明确约定不作逐字节对比。这是「旧批次没有某字段就 fail-closed」能成立的前提——每一批的数据自洽。

**4. 断点续跑**
长跑必须假设会中断——用完成清单（manifest）逐场记录「这套阵容乘这颗种子已经跑完」，重启后直接跳过。两次全量长跑、合计十四个分段，完成清单零重复键，续跑全部成功。

## 判红分析器：随仓开源，样例可复现

闭源的只有引擎与仿真脚手架（Java 侧）；**判红分析器随本仓完整开源**（纯 Python 标准库，零第三方依赖），并附真实批次样例（脱敏）——本文档的判红规则不是文字主张，是可以跑出来验证的代码。

```
├── tools/analyze.py                 ← 判红分析器（五级判红 + Wilson 置信区间，纯标准库）
├── tools/check_anomalies_schema.sh  ← 异常清单 schema 校验（fail-closed）
├── scripts/run_sim_gate.sh          ← 门禁编排形态参考（跑量步依赖闭源引擎）
└── data/
    ├── sample-games/                ← 3 局真实批次样例（脱敏）+ 进度文件
    ├── sample-anomalies.jsonl       ← 真实异常样例（quality 级：记录不判红）
    └── sample-lineups.json          ← 演示用阵容清单（与真实批次 schema 同构）
```

复现命令：

```bash
# 判红（预期退出码 0「绿」：样例无硬异常，coverage warn 档高亮但不判红）
python3 tools/analyze.py data/sample-games --exit-code --lineups data/sample-lineups.json --coverage warn

# 异常清单 schema 校验（fail-closed 演示：把任一行 severity 改成非法值再跑，即判失败）
bash tools/check_anomalies_schema.sh data/sample-anomalies.jsonl
```

## 长跑工程坑实录

10 万场级的长跑里，Java 运行进程（JVM）一共停滞过三次，症状相同：完成清单不再增长、八个线程 CPU 打满——进程活着，不报错，就是不干活。三次根因各不相同：测试替身（mock）在内存里逐场堆积，两万多场时撑爆了类的元空间；调度器的假对象越攒越多，三万多场时重蹈覆辙；共享假对象的调用记录无界累积，把老年代堆到 99.96%、垃圾回收连发。按「同一问题连修三次未根治就停手换方案」的卡点规则，第四次修复尝试叫停，降级为每 8 分钟强制换新进程分段跑完，剩余五点九万场分五段收工。教训写进脚本默认行为：**长仿真默认分段运行，信任完成清单，不信任进程。**顺带一个反直觉实测：单场对局只要约 74 毫秒，十万场的纯计算量是二三十分钟级——最初「4 到 11 个小时」的悲观预估差点骗我绕开正确的路。

每行读法：该将出场全部对局（每将约 4.1 万场）聚合出的胜率与场均数据。另产出 15×15 搭档矩阵（同队胜率相对两将各自基线的增减，量协同/相克信号）、阵容梯度（Top/Bottom 清单）等报表。聚合数据口径：每场对局在进程内归约为一行 JSON（胜负/回合数/双方每将各档技能兑现次数/伤害构成四类/出牌计数），schema 冻结。分析器同时输出胜率矩阵的 Wilson 95% 置信区间与策略间显著性判定（≥50 局、区间不重叠才记显著）——小样本的「看起来赢」不进结论。

> 数据说明：以上为仿真自对弈（455 阵容 × 103,740 场，双方同源 AI、自动配牌）的聚合结果，**非真实玩家数据，也非最终平衡结论**——报告自身口径即为「总评：有顾虑」，量出梯度正是评估的目的：先有可信的尺子，才谈得上调整。

## 不开源说明

闭源的是权威战斗引擎本体与其仿真脚手架（Java 侧，脚手架直接驱动引擎自对弈）；**判红分析器（tools/analyze.py）与样例数据随仓开源**。因此本仓提供：可运行的判红分析器、门禁口径、判红规则、设计结构与脱敏聚合报表样例；不提供引擎源码与可执行仿真脚手架。样例数据全部为仿真自对弈聚合结果，不含任何真实玩家数据。
